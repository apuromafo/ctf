## 题目名称

SokobanHTB —— 利用逆向分析与内存修改获取游戏通关 Flag

---

## 题目背景与目标

给定一个 Windows 小游戏 **SokobanHTB.exe**，界面类似简化版推箱子（Sokoban）：

* 紫色小人：玩家，可用 **WASD** 或方向键移动
* 绿色方块：可以推动的箱子
* 黄色 `X`：目标位置

从画面和常识推断：**需要把三个绿色方块推到三个黄色 `X` 上，才能触发通关并得到 flag**。

题目要求：通过逆向、内存修改等手段快速拿到 flag，并写出分析过程。

---

## 使用工具

* **Ghidra**：静态反汇编 / 反编译，分析游戏逻辑
* **Cheat Engine 6.7**：动态内存扫描与修改，用于寻找和篡改坐标

---

## 解题过程（对应 1～11 张图）

### 1. 运行程序，初步体验规则

打开 SokobanHTB 界面：

* 使用 **WASD** 可以控制紫色小人移动
* 绿色方块会被推动
* 黄色 `X` 看起来是箱子要到达的目标点

推测题目要求：**把三个箱子推到三个 `X` 上**。

---

### 2. 尝试直接修改“分数”失败

先用 Cheat Engine 走常规思路：

* 观察游戏中是否有明显的分数 / 计数变化（例如推箱次数、到达目标数）
* 在 CE 中按 0→1→2 的变化去搜整数、字节等

多次扫描后，没有找到稳定对应的内存地址，**简单的“搜分数”方案失败**。于是改为逆向配合坐标思路。

---

### 3. 使用 Ghidra，从 `entry` 入口分析

将可执行文件导入 Ghidra，找到程序入口 `entry`：

```c
void entry(void) {
    __security_init_cookie();
    FUN_1400b32e0();
    return;
}
```

可以看到真正的逻辑从 `FUN_1400b32e0()` 开始。

---

### 4. 分析 `FUN_1400b32e0`，锁定主函数

在 `FUN_1400b32e0()` 中发现一段关键代码：

```c
iVar2 = FUN_1400045f0();
uVar5 = FUN_1400b432c();
if ((char)uVar5 != '\0') {
    if (!bVar1) {
        _cexit();
    }
}
__scrt_uninitialize_crt(...);
return iVar2;
```

其中 `FUN_1400045f0()` 的返回值最终作为程序返回值，而它在初始化后立刻被调用，**推断 `FUN_1400045f0()` 为游戏主函数**。

---

### 5. 反编译 `FUN_1400045f0()`，发现坐标初始化

对 `FUN_1400045f0()` 进行反编译和伪代码整理，逻辑大致如下：

1. 初始化本地变量、locale、字符串等
2. 加载字体
3. 加载贴图 `player.png`（玩家）
4. 加载贴图 `X.png`（目标位置）
5. 加载贴图 `box.png`（箱子）
6. 初始化地图数据（8×7）
7. 根据地图堆叠对象：玩家、目标、箱子、墙
8. 进入 `while (running)` 游戏循环：

   * 处理输入（WASD / 方向键）
   * 更新玩家位置
   * 判断是否撞墙 / 撞箱子
   * 判断箱子是否能被推动
   * 判断箱子是否都在目标点上
   * 绘制画面

在初始化地图对象时，每次都会调用：

```c
FUN_140018fb0((longlong)local_670, CONCAT44((float)i, (float)j));
```

这里传入了一对 `float`，很像 `(x, y)` 坐标。由此推断：

> **玩家和箱子的位置信息使用单精度浮点坐标保存在内存中。**

---

### 6. 第一次内存扫描：未知的浮点值

根据上一步的推断，用 CE 启动**坐标扫描**：

* **Value Type**：选 `Float`（单精度浮点）
* 因为一开始不知道具体值，扫描类型选择 **“Unknown initial value（未知初始值）”**，做第一次全局扫描。

接着，通过控制人物移动配合二次扫描来缩小范围。

---

### 7. 锁定玩家 x、y 坐标地址

继续在 CE 中操作：

1. 控制人物**向右移动**，在 CE 中选择 **“Increased value”** 再次扫描；
2. 控制人物**向左移动**，选择 **“Decreased value”** 再扫描；
3. 不移动时，选择 **“Unchanged value”** 过滤；

多轮之后，候选地址数量大大减少。

然后：

* 把剩余地址全部双击加入下方地址列表；
* 逐个修改这些地址的值，观察游戏中人物是否瞬移。

最终发现：

* 修改某个地址的数值时，人物**水平位置**会立刻发生变化 → 判定为 **x 坐标地址**。
* 随后根据结构体排列的常见习惯，推测 y 坐标在 `x_addr + 4` 处：

  * 在 CE 中新增地址：`x_addr + 4`，类型仍为 `Float`；
  * 修改这个地址，发现人物**竖直位置**发生变化 → 判定为 **y 坐标地址**。

验证完毕后，将其它多余的候选地址全部删除，仅保留这两个坐标地址。
在它们附近做 `±4` 的偏移查看是否有其它有用字段，结果没有发现更多明显数据。

---

### 8. 确定外圈方块的大致坐标（发现 1024）

锁定了玩家坐标后，下一步是找到**外面那些方块（箱子/障碍）**的坐标。思路：

1. 在 CE 中直接把玩家的 **x 坐标改成很大的值**，让人物冲出地图边界；
2. 观察游戏行为，发现当 x 被改得太大时，人物会被游戏逻辑立即传回地图里；
3. 通过不断调试，最终发现：

   > 当玩家 x 坐标约为 **1024** 时，人物刚好与外侧某个方块重合。

因此推测：**1024 是外圈方块或边界所在的一个关键 x 坐标值**。

---

### 9. 围绕 1024 进行反复扫描，锁定箱子/方块数组

以 1024 为线索，再次使用 CE 进行精确扫描：

1. Value Type 仍为 `Float`；
2. 第一次扫描：搜索 **Exact value = 1024**；
3. 然后在游戏中做少量操作（例如推箱、轻微位移）配合：

   * 对应变化用 “Increased/Decreased”
   * 不受影响的用 “Unchanged”

反复筛选后，内存中只剩下少量为 1024 的地址。

将这些地址全部加入列表，逐个修改并观察：

* 修改某些地址时，画面中外圈的方块会移动或消失；
* 由此可以确认，这些地址属于**外部方块 / 箱子 / 障碍物的坐标数组**。

---

### 10. 定位真正影响胜负的三个箱子坐标

此时我们知道：

* 玩家坐标地址：`player_x`, `player_y`；
* 若干外圈方块 / 箱子的坐标地址，其中有一部分是装饰或边界用；

接下来要做的是：**从这些地址里挑出那三个真正参与“是否通关”判断的箱子坐标**。

方法：

1. 在游戏中先观察哪几个绿色方块是“可推到 X 上”的箱子；
2. 在 CE 中，对那些坐标地址逐个修改：

   * 若改动一个地址时，某个可推动的箱子会瞬移或位置异常，则该地址就是该箱子的 x/y；
3. 同理对 y 坐标进行验证；
4. 依次锁定三个真正参与判定的箱子坐标。

这一步就是第 10 步里“对 1024 进行反复扫描得到结果，并同样依次修改确定”的过程——通过多次修改和观察，**把每个坐标与具体箱子一一对应起来**。

---

### 11. 篡改箱子坐标到目标点，触发通关并得到结果

当三个箱子坐标都被确定后，就可以直接**作弊通关**：

1. 先通过试探或从代码中得知三个黄色 `X` 对应的目标坐标（x,y）；
2. 在 CE 中，把三个箱子的 `(x, y)` 坐标**直接改成对应目标点的坐标**，让它们在内存中“瞬移”到 `X` 上；
3. 返回游戏界面，轻微移动一次玩家或等待画面刷新，使主循环重新进行“箱子是否都在目标点上”的判断；
4. 条件满足后，程序会执行胜利分支，在屏幕上绘制出最终 flag。


```text
HTB{H4ck_0r_50k084n_7h3_80x_a34fbe06}
```

---

## 经验与收获

* 学会了如何从 **入口函数 → 框架初始化 → 主循环** 的顺序去阅读逆向工程项目；
* 通过反编译代码，能从函数参数形式（如 `CONCAT44((float)i, (float)j)`）推断出内部数据结构含义（这里是坐标）；
* 熟练运用了 Cheat Engine 的几种常用扫描方式：

  * Unknown initial value
  * Increased / Decreased / Unchanged
  * 精确值反复扫描
* 通过“坐标 + 边界值（1024）”的综合利用，成功定位了关键对象数组，并最终通过内存篡改绕过正常游戏流程拿到 flag。

HTB{H4ck_0r_50k084n_7h3_80x_a34fbe06}
